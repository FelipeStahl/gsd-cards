# Phase 4 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** This is the DELTA on top of `.planning/phases/01-espelho-fiel/01-UI-SPEC.md`, `.planning/phases/02-sess-o-viva/02-UI-SPEC.md`, and `.planning/phases/03-board-interativo/03-UI-SPEC.md`. All three prior contracts (spacing scale, typography scale, color tokens, `statusDotVariants`/`StatusTone` 4-tone system, `ActivityDot`, `status-dot--pulse`/`--outline` modifiers, desktop-only scope, xterm theme, i18n-keys-from-day-one rule) are the standing contract and are **reused verbatim**, not redefined. This document only specifies what Phase 4 adds: the home/landing screen (PROJ-01/PROJ-06), the create-project affordance (PROJ-03), the project switcher (PROJ-05), restored/persistent session visual language (SESS-04), the rename-session affordance (SESS-05), and notification/badge treatment for awaiting/exited sessions (TERM-04).

**Mode note:** `04-CONTEXT.md` exists (smart discuss, `--auto`, recommended answers auto-accepted) and is treated as the standing locked decision set — its `## Implementation Decisions` are NOT re-litigated here, only translated into pixel/copy/state contract. `04-CONTEXT.md`'s `## Claude's Discretion` items (store file layout, snapshot storage location, home layout grid-vs-list, awaiting-notification debounce) are resolved below with documented defaults and logged in `## UI Considerations` as `backstop`/`unresolved` where real ambiguity remains. Generated in autonomous mode (`--auto`) — no user was interrupted with questions.

**Invariant restated for this phase's UI (from `04-CONTEXT.md` `## Phase Boundary`):** the home screen, recents list, and all persistence introduced this phase read/write only the app's own `appDataDir` (via `@tauri-apps/plugin-store`) — never `.planning/`. Creating a project happens by injecting `/gsd-new-project` into a real terminal session, never by the app writing files directly. No new visual surface in this phase implies or suggests in-app editing of GSD artifacts.

## Spacing Scale

Unchanged — reuse the Phase 1 scale verbatim (`xs` 4px through `3xl` 64px, all multiples of 4). See `01-UI-SPEC.md` `## Spacing Scale`.

Exceptions this phase (additive, documented deliberately, not scale violations):

| Element | Value | Reason |
|---|---|---|
| Project card (home grid) | padding **24px** (lg), min-height **140px**, radius 8px | A page-level card (not a dense board card) — more breathing room than `PhaseCard`'s 16px, matching the "landing screen, not a dense operational view" posture; radius matches `PhaseCard`'s existing 8px for visual family resemblance |
| Home grid gap | **24px** (lg) between cards, both axes | One step up from the board's 16px column gap — home has fewer, larger items per viewport |
| Rename inline-edit input | height **28px** | Sized to sit inline in the existing 40px `SessionRow` without changing row height — matches the row's Label-size text baseline, smaller than the 32px icon-button standard because it's a text input replacing a text label, not a standalone control |
| Header project-switcher control | height **32px** | Same icon-only/compact-control exception already established for `TerminalPane` chrome buttons (Phase 2) — sits in the existing 56px `Header` bar |
| Sidebar scope banner (project-switch context line) | height **24px** | Thin informational strip, not an interactive control — content-driven height (Label 12px/600 + 4px padding), same sizing logic as `PhaseCardAction`'s content-driven 24px in Phase 3 |
| Notification badge (DrawerRail rail icon) | **16px** diameter, positioned top-right of the 48px rail icon | Superscript-badge convention already implied (but not yet built) by Phase 2's "small accent-colored numeric badge" language for the live-session count — Phase 4 formalizes the exact size and extends it to carry needs-input/exited state, not just a count |

## Typography

Unchanged — reuse the Phase 1 4-role scale verbatim (Label 12px/600, Body 14px/400, Heading 18px/600, Display 24px/600, only weights 400/600 anywhere). See `01-UI-SPEC.md` `## Typography`.

**New usage mapping this phase:**

- **Label** (12px/600): project card phase-name/status text, project card blocker-count badge, home CTA subtext ("Escolha uma pasta"), sidebar scope banner text, rename inline-edit hint, restored-session badge text ("histórico restaurado"), notification badge count (if numeric)
- **Body** (14px/400): home empty-state body, create-project progress/feedback body, project-card error body ("pasta não encontrada"), rename inline-edit input text itself, restored-session tooltip body
- **Heading** (18px/600): home page heading ("Projetos recentes"), create-project modal/panel heading, project-switcher dropdown header (if used)
- **Display** (24px/600): not introduced by any new Phase 4 element on the home screen itself — deliberately kept at Heading (18px) for "Projetos recentes" rather than Display, because the home screen is a utility launcher, not a branded landing page; Display stays reserved for the in-project `Header`'s project name (Phase 1), preserving Display's rarity/weight in the overall type system

## Color

Unchanged tokens — reuse the Phase 1 palette + Phase 2/3's `StatusTone`/`statusDotVariants`/`ActivityDot`/pulse system verbatim. See `01-UI-SPEC.md` `## Color`, `02-UI-SPEC.md` `## Color`, `03-UI-SPEC.md` `## Color`. **No new `StatusTone` value is introduced this phase.**

**Project-card health color mapping (PROJ-06)** — reuses the exact same tone semantics as the board's `StatusBadge`/`ProgressBar`, applied at project-summary granularity instead of phase granularity:

| Project card state | Tone | Visual |
|---|---|---|
| Healthy (readable STATE.md, no blockers) | `success` (progress bar fill), neutral text otherwise | Reuses Phase 1's `ProgressBar` component verbatim (accent fill per Phase 1, NOT success — see note below) |
| Has pending blockers | `warning` | Small `AlertCircle` icon (14px) + Label-style blocker count, warning-tinted, inline next to the phase name — same restrained "icon + text, never a fill" discipline as `PhaseCard`'s existing blocked badge |
| Loading (health being read, lazy) | `neutral` | Skeleton/placeholder treatment — see `## Home Screen — States` |
| Error (moved/deleted project) | `destructive` | `AlertCircle` icon in `--color-destructive`, card border switches to a thin destructive-tinted 1px border, card becomes non-primary-clickable (see `## Home Screen — States`) |

**Correction note (keeps consistency with Phase 1, not a new rule):** the project card's own progress bar reuses Phase 1's `ProgressBar` exactly as declared in `01-UI-SPEC.md` `## Header Bar Detail` — **accent** fill, not success — because Phase 1 never introduced a "success-colored progress" variant and this phase does not invent one. "Healthy" above refers to the absence of a blocker/error badge, not a color change on the bar itself.

**Restored-session visual language (SESS-04)** — extends the existing `SessionRowVariant`/`TONE_BY_VARIANT` system (`SessionRow.tsx`) rather than adding a new variant:

| Session state | `SessionRowVariant` | Tone | Visual delta this phase |
|---|---|---|---|
| Live process, this app run | `live` | `success`/activity-aware (unchanged from Phase 2/3) | No change |
| Restored from a previous app run, not yet re-activated | `historical` (reused — this is exactly what `historical` already meant: "no live `PtySession` backing it this app run") | `neutral`, `--outline` modifier (unchanged dot rendering) | **New:** row gains a small `History` icon (14px, muted foreground) to the left of the timestamp, replacing Phase 2's plain hollow dot as the sole "not live" signal — the icon is the net-new visual delta that reads as "this is history, lazily resumable" at a glance, distinct from "sessão nunca aberta nesta execução" language Phase 2 used generically. Row remains clickable; click now actually resumes (`claude --resume`) instead of showing Phase 2's placeholder tooltip (`session.row.historicalTooltip` copy is retired — see `## Copywriting Contract`) |
| Restoring (user clicked a restored row, `claude --resume` spawning) | `starting` (reused, unchanged tone/pulse) | `accent`, pulse | No change — Phase 2's existing "starting" treatment already covers this exactly; restoring a historical session and starting a brand-new one look identical while in flight, which is correct (the user doesn't need to distinguish "cold spawn" from "resume spawn" while waiting) |
| Exited (process ended) | `exited` (reused, was idle/unused until this phase) | `warning`, static | Row gains the exited suffix copy (already defined `session.row.exited` in Phase 2) — **first phase this variant is actually driven by a real signal** (Rust→JS exit event, per `04-CONTEXT.md`); previously idle/theoretical |

**Accent (10%) additionally reserved for, this phase:** the "Novo projeto" home CTA button, the "Abrir pasta" secondary CTA, the project-switcher control's active/hover state, the rename inline-edit input's focus ring, the selected project card's hover border (same 1px accent-border-on-hover convention as `PhaseCard`). Still never a large fill or body text color.

**Destructive reserved for:** the moved/deleted project card's error icon+border (new this phase — the first non-session-delete consumer of the destructive token), unchanged Delete-session confirm dialog fill from Phase 2.

**Notification badge tone mapping (TERM-04):**

| Badge trigger | Tone | Where |
|---|---|---|
| ≥1 session `awaiting` (needs input) | `accent` | Rail badge (16px dot, filled) — takes priority display over a plain live-count badge when both would apply, since "needs you" is more actionable than "still running" |
| ≥1 session `exited` since last viewed | `warning` | Rail badge (16px dot, filled) — shown only if no `awaiting` session exists (accent wins the priority) |
| Only live/idle sessions, no awaiting/exited | `accent`, numeric | Unchanged Phase 2 behavior — plain count badge |
| No live sessions | none | Badge not rendered, rail returns to Phase 1's fully passive disabled/tooltip state |

## Home Screen — Layout

New top-level view, entered when no project is active (`view === "home"` per `04-CONTEXT.md`'s "novo view-state" decision — no router). Replaces the entire `AppShell` render (header+sidebar+board+drawer do not mount while on the home screen).

```
┌─────────────────────────────────────────────────────────────────┐
│ Home header — 56px, dominant surface, 24px (lg) horizontal pad   │
│ [Projetos recentes · Heading]      [Abrir pasta] [+ Novo projeto]│
├─────────────────────────────────────────────────────────────────┤
│                                                                     │
│  32px (xl) outer padding, dominant surface                        │
│                                                                     │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐            │
│  │ Project card  │  │ Project card  │  │ Project card  │  ...      │
│  │ 24px padding  │  │ 24px padding  │  │ 24px padding  │            │
│  │ min-h 140px   │  │ min-h 140px   │  │ min-h 140px   │            │
│  └──────────────┘  └──────────────┘  └──────────────┘            │
│  ← 24px (lg) gap both axes, cards min-width 280px, wrap →         │
│                                                                     │
└─────────────────────────────────────────────────────────────────┘
```

- Grid, not list (this researcher's resolved default for CONTEXT's discretion item — see `## UI Considerations`): `grid-template-columns: repeat(auto-fill, minmax(280px, 1fr))`, matching `BoardColumn`'s existing 280px min-width convention for visual family resemblance across the app's two card-grid surfaces.
- Home header CTAs mirror `Header`'s existing button-placement convention (Phase 1: right-aligned actions) but at the home level, before any project is open — "Abrir pasta" is Body-style secondary (outline/ghost), "Novo projeto GSD" is the accent-filled primary CTA, consistent with the one-primary-CTA-per-screen discipline established since Phase 1.
- Below min comfortable width (1024px, same threshold as the board): grid still wraps/reflows normally (unlike the board, which explicitly refuses to shrink columns) — the home screen is a simpler content type where reflow is safe and preferred over horizontal scroll.

## Project Card Anatomy (PROJ-01, PROJ-06)

Reuses `PhaseCard`'s established visual family (secondary surface, 8px radius, accent-border-on-hover, entire card clickable) at page-card scale (24px padding vs. 16px).

Top to bottom:
1. Row 1: project name (Heading 18px/600, truncate + tooltip) — derived from `deriveProjectName` (existing `board-store.ts` helper, unchanged)
2. Row 2 (once loaded): current phase name (Body 14px/400, muted) — e.g. "Fase 3: Board interativo"
3. Row 3 (once loaded): `ProgressBar` (reused verbatim from Phase 1's `Header Bar Detail`, accent fill) + `home.card.progress` text right-aligned, same 4px-track/accent-fill treatment as the in-project header
4. Row 4 (only if blockers > 0): `AlertCircle` (14px, warning) + `home.card.blockers_one`/`_other` (Label style, warning-tinted) — omitted entirely when zero blockers (no "0 bloqueios" noise row), same "don't reserve empty space" discipline as Phase 3's `complete`-status card
5. Loading variant: Rows 2–4 replaced by a single `home.card.loading` line + a muted skeleton bar (simple `color-mix` pulse, reusing the `.status-dot--pulse` animation timing on a bar shape instead of a dot — no new animation curve)
6. Error variant: Rows 2–4 replaced by `home.card.error.heading`/`.body` (destructive-tinted `AlertCircle` + text) + the two error actions (`home.card.error.remove` / `.retry`, small Label-style text buttons, neutral + accent respectively)

Click target: entire card (healthy/loaded state only) — calls the existing `openProject(root)` flow (`board-store.ts`), then transitions `view` from `"home"` to the in-project shell. Error-state cards are NOT primary-clickable (see `## UI Considerations`).

Real-time update: no live-glow treatment this phase (Phase 1's 1000ms accent glow is a board-specific, file-watcher-driven behavior; the home screen reads health lazily on mount, not via a live watcher — re-visiting the home screen re-reads health fresh each time, no persistent background watching of non-active projects).

## Create-Project Flow (PROJ-03)

Triggered by the home header's "Novo projeto GSD" CTA. No new modal component — reuses the `ConfirmDialog`-style small centered panel pattern (per `02-UI-SPEC.md` `## Session Lifecycle Affordances`) for the progress/feedback states, since this is a short-lived, dismiss-on-completion flow, not a persistent page.

Sequence:
1. Click CTA → OS-native folder picker opens immediately (`open({ directory: true })`), prompt copy `home.create.pickerPrompt` shown as the dialog's own title where the OS API supports a title string, otherwise omitted (OS-owned chrome, not fully stylable — documented so executor doesn't try to force it)
2. Folder chosen → small centered panel (`ConfirmDialog` skeleton, no destructive tone) shows `home.create.progress.heading`/`.body` with a `Loader2` spinner (reused from Phase 2's starting-session spinner), no cancel action once the session/injection has started (consistent with the app's existing "no confirmation friction on process actions" posture)
3. Folder chosen but not empty (validated by the create-project code path, not `validate_project_root`'s normal `.planning/`-required check — per `04-CONTEXT.md`'s separate registration path) → panel instead shows `home.create.error.notEmpty.*`, single "OK" dismiss returns to home, picker can be re-opened
4. Success (watcher detects `.planning/` now exists) → panel auto-dismisses, app transitions the user directly into the new project's board (same `openProject` flow as clicking a healthy recent card) — no separate "success" screen, the working board IS the success state

The panel never blocks the ability to see terminal output — if the user wants to watch `/gsd-new-project`'s own prompts/output live rather than wait on the progress panel, the panel includes no modal backdrop-blocking of keyboard input to the terminal underneath (soft overlay only, matching `CommandPalette`'s "board never fully blocked" precedent from Phase 3) — this is a deliberate reuse of Phase 3's "confined, non-blocking overlay" posture rather than Phase 1/2's full-viewport modal posture, because the user may need to interact with the terminal (e.g. answer a `/gsd-new-project` prompt) while this panel is visible.

## Project Switcher (PROJ-05)

New control in the in-project `Header` (extends `01-UI-SPEC.md` `## Header Bar Detail`), left of the project name, since "return to home" is the most structurally primary navigation action in a multi-project app:

```
[← Home icon, 32×32]  [Project name · Display]  [Milestone badge]  ...  [Sync indicator]
       ^ new
```

## Rename Session (SESS-05)

Extends `SessionRow`'s existing hover-action pattern (`Archive`/`Trash2`, per `02-UI-SPEC.md` `## Session Sidebar & Row Anatomy`). Adds a third 32×32 hover button, `Pencil`, positioned first (leftmost) in the hover-action group — rename is non-destructive and more frequently used than archive/delete, so it gets primary position:

```
Row hover state (extends Phase 2 anatomy):
[●] [Sessão a3f91c2d]        [há 2 min]  [✏ Renomear] [Archive] [Trash2]
                                           ^ new, 32×32, neutral icon
```

**Inline-edit interaction (chosen over a dialog — lighter-weight, consistent with the row's own compact density):**
1. Click `Pencil` → row's label region swaps from static text to a 28px-height text input (`session.rename.placeholder` when empty, pre-filled with the current display name or empty if none set), auto-focused, text selected
2. Two small inline icon affordances appear at the input's trailing edge: `Check` (confirm, 20px, accent) and `X` (cancel, 20px, muted) — both within the row's existing 40px height, no row-height change
3. `Enter` or clicking `Check` → calls `renameSession(id, name)` (per `04-CONTEXT.md`'s store action), row returns to static-label display showing the new name; empty input on confirm clears the name (row falls back to the derived `"Sessão " + id.slice(0,8)` label, per CONTEXT's "Label cai para o derivado... quando não há nome")
4. `Esc` or clicking `X` → discards the edit, row returns to static-label display unchanged
5. Renamed sessions display the custom name in place of the derived id-based label everywhere the label appears (row, `TerminalPane` chrome header, `DetailPanel`'s "Enviar para:" caption from Phase 3) — the underlying id-based derivation remains the tooltip/title-attribute fallback for disambiguation, never fully hidden

No `ConfirmDialog` involved — renaming is reversible/low-stakes, consistent with Archive's "no confirmation" treatment rather than Delete's confirmed-destructive treatment.
