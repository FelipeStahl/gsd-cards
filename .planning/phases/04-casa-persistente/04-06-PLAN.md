<objective>
SESS-04: sessions survive closing and reopening the app and restore lazily. This plan carries the phase's **critical security control** — the flag-injection guard — and the split-file snapshot persistence.

The mechanism: on lose-focus/exit, serialize each session's xterm buffer (via the already-installed `SerializeAddon`, already wired in-memory in `focus-algorithm.ts`) to its OWN `session-<id>.json` (per 04-RESEARCH Pitfall 4 — never the same file as hot metadata), and persist session metadata (id, projectRoot, name, lastActive) in `app-state.json`. On reopen, persisted sessions appear as **restored** rows (History icon, "histórico restaurado, não processo contínuo") scoped to their project — the PTY does NOT re-spawn eagerly. Only when the user clicks a restored row does `resumeSession` fire: validate the id, load its snapshot, spawn `claude --resume <id>` in the session's OWN cwd, and rehydrate the snapshot into a fresh xterm BEFORE the first resume byte arrives.

**Critical threat (T-04, the phase centerpiece):** the persisted, locally-tamperable session id becomes a `claude --resume <id>` argv value. A crafted id starting with `-`/`--` can be reparsed as a different CLI flag by Claude Code's own arg parser (portable-pty spawns with no shell, so this is argv reinterpretation, not shell injection). Mitigation: a STRICT UUID allow-list (`isValidSessionId`, mirroring Phase 3's `sanitizePhaseId`) applied at the SINGLE point the id enters `spawnSession`'s args — a flag-shaped id is rejected before it ever reaches `invoke`. This is modeled with a checkable acceptance criterion (a leading-dash id is rejected).

Output: `id-format.ts` (the guard), `session-snapshot.ts` (per-session store), `resumeSession` + restored-session lifecycle, and the snapshot save/rehydrate wiring.
</objective>

## Phase Goal (user story)

**As a** GSD user, **I want to** reopen the app and find my previous sessions restored — visibly marked as history and resumable on click — **so that** closing the app never loses my work and reopening it is cheap. *(Derived from ROADMAP Phase 4 Success Criterion #4.)*

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| persisted session id (app-state.json) → claude --resume argv | Locally-tamperable string becomes a process argument |
| persisted projectRoot → resume cwd | Determines which conversation store --resume searches |
| session-<id>.json snapshot → xterm.write | Tampered snapshot bytes written to the terminal surface |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-16 | Tampering / Elevation of Privilege | Persisted session id used as `claude --resume <id>` argv value (FLAG INJECTION — phase centerpiece) | critical | mitigate | Strict UUID allow-list `isValidSessionId` applied at the single point the id enters `spawnSession`'s args, BEFORE `invoke` — a `-`/`--`-leading (flag-shaped) id is rejected and never reaches argv (checkable acceptance criterion). No shell involved (portable-pty), so this is the complete surface |
| T-04-17 | Tampering | Persisted projectRoot used as resume cwd | high | mitigate | resumeSession reads the session's OWN persisted projectRoot (never activeProjectRoot — Pitfall 2); the path is the already-validated project root, and a wrong/deleted one yields a clean exit (T-04-18) rather than a crash |
| T-04-18 | Denial of Service | Failed `--resume` (deleted transcript / wrong cwd) | low | accept | A failed resume exits near-instantly and flips the row to `exited` via the 04-02 pty:session-exited event — no special-casing, a clear "clicked resume, immediately exited" signal (Pitfall 3) |
| T-04-19 | Tampering | Tampered session-<id>.json snapshot written to xterm | low | accept | Snapshot is terminal display bytes written to the app's own xterm surface (same trust as any terminal output); no code execution path; local-desktop threat model, same-OS-user |
</threat_model>
