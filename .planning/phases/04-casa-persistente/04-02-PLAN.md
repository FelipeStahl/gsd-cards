<objective>
Backend foundation for SESS-04 (lazy resume via `claude --resume`) and TERM-04 (exit detection). Two net-new backend mechanisms, both mirroring existing precedents so they de-risk early alongside the persistence tracer:

1. **`--resume` argv passthrough** — `spawn_session` (Rust) and `spawnSession` (channel.ts) gain an `args` parameter threaded straight into `CommandBuilder::args`. Empty for a normal new session (existing SESS-02 call sites unaffected); `["--resume", id]` for lazy restore (consumed by 04-06).
2. **PTY exit event (Rust→JS)** — today the reader thread just `break`s on EOF and emits nothing, so a naturally-exited session leaves a stale `PtyManager` entry that permanently blocks re-spawning the same id (fatal for lazy restore, which reuses persisted ids). Extend the reader-thread closure to purge the dead entry via a new pure `PtyManager::remove_exited` and emit a global `pty:session-exited` event — mirroring `planning_watcher.rs`'s `app.emit("planning:changed", ...)` precedent, NOT a tagged envelope inside the raw-bytes `Channel<Vec<u8>>` (which must stay a pure byte pipe for xterm.js).

Purpose: proving the Rust→JS exit signal and the argv passthrough now (does `remove_exited` free the id? does the emit fire after `pump_pty_output` returns?) means 04-06 restore and 04-07 notifications build on a proven backend instead of discovering the reader thread can't emit after ten committed UI layers.

Output: `spawn_session` args param, `PtyManager::remove_exited`, reader-thread purge+emit, `channel.ts` `spawnSession(args)` + `listenForSessionExit`. No frontend consumption yet — 04-06/04-07 wire the listener into the store.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| frontend args array → CommandBuilder argv | A value placed in `args` becomes a real process argument (no shell) |
| Rust reader thread → global event bus | Exit signal broadcast to all frontend listeners |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-04 | Tampering / Elevation of Privilege | `spawn_session` args forwarded to `CommandBuilder::args` (`--resume <id>`) | critical | mitigate | `portable-pty` spawns with no shell (no metacharacter injection), but a `-`-leading argv VALUE can still be reparsed as a flag by Claude Code's own parser. This plan forwards args verbatim by design; the allow-list guard (`isValidSessionId`) that gates what may enter this array is enforced at the single frontend call site in 04-06 BEFORE `invoke`. Documented here so the passthrough is never treated as safe on its own. |
| T-04-05 | Denial of Service | Stale PtyManager entry after exit permanently blocks re-spawn of the id | high | mitigate | `remove_exited` purges the dead entry in the reader thread so lazy-restore (which reuses persisted ids) can re-spawn; poison-safe lock never wedges cleanup |
| T-04-06 | Tampering | Exit signal contaminating the raw-byte Channel wire format | low | mitigate | Exit travels as a separate global `tauri::Emitter` event; the byte Channel is untouched (verified by acceptance grep) |
</threat_model>
