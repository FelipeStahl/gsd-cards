# Phase 5 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** This is the DELTA on top of `01-UI-SPEC.md`, `02-UI-SPEC.md`, `03-UI-SPEC.md`, and `04-UI-SPEC.md`. All four prior contracts (spacing scale, typography scale, color tokens, `statusDotVariants`/`StatusTone` 4-tone system, `.status-dot--pulse`/`--outline` modifiers, desktop-only scope, i18n-keys-from-day-one rule, "Tool: none" manual Tailwind 4 + `class-variance-authority` system, `ProjectSwitcherButton`'s icon-button precedent, `SyncIndicator`'s dot+label+inline-action recipe) are the standing contract and are **reused verbatim**, not redefined. This document only specifies the two visual surfaces Phase 5 adds: the `LanguageSwitcher` (DIST-01) and the update-available affordance (DIST-03).

**Mode note:** `05-CONTEXT.md` exists (smart discuss, autonomous, recommended answers auto-accepted) and is treated as the standing locked decision set — its `## Implementation Decisions` are NOT re-litigated here, only translated into pixel/copy/state contract. `05-CONTEXT.md`'s `## Claude's Discretion` items (toggle vs. dropdown shape, exact update-notice UX) are resolved below with documented rationale, not re-asked. Generated in autonomous mode (`--auto`) — no user was interrupted with questions; genuine open ambiguity is logged in `## UI Considerations` as backstop, not silently assumed.

**Why this UI surface is small (deliberate, not incomplete):** per the orchestrator's framing, Phase 5 is distribution-focused — DIST-02 (bundler/installer/CI) is 100% config and has **zero visual surface** (see `## DIST-02 — No UI` below, included so the checker doesn't flag it as a missing spec). The only new pixels this phase are a language toggle and a non-intrusive update notice.

## Color

Unchanged tokens — reuse the Phase 1 palette + Phase 2/3's `StatusTone`/`statusDotVariants` system verbatim. See `01-UI-SPEC.md` `## Color`. **No new `StatusTone` value is introduced this phase** — the update affordance reuses exactly the two tones the system already defines for "something needs attention" (`accent`) vs. "something degraded" (`warning`), the same split `04-UI-SPEC.md`'s notification badge already established.

| Element / state | Tone | Reasoning |
|---|---|---|
| `LanguageSwitcher` active segment | `accent` fill (`var(--color-accent)`), white text | Same accent-for-active-state convention as the card hover border / active nav affordances elsewhere in the app |
| `LanguageSwitcher` inactive segment | neutral foreground at 0.7 opacity, transparent background | Matches `SyncIndicator`'s `LABEL_STYLE` muted-text convention (`opacity: 0.75`) |
| `LanguageSwitcher` container border | `var(--color-secondary)`, 1px | Reuses `HomeScreen.tsx`'s existing `ctaSecondaryStyle` border recipe verbatim (see `## Language Switcher` note on the one accepted context-tradeoff) |
| `UpdateIndicator` available/downloading | `accent` dot (`statusDotVariants({tone:"accent"})`) | "Something worth your attention, not urgent" — same semantic Phase 4 assigned to the `awaiting`-session rail badge |
| `UpdateIndicator` error | `warning` dot (`statusDotVariants({tone:"warning"})`) | Same semantic as every other degraded/blocked state in the app (stale sync, blocked phase, exited session) |

**Accent (10%) additionally reserved for, this phase:** the `LanguageSwitcher`'s active-segment fill, the `UpdateIndicator`'s "Atualizar e reiniciar" inline text-button and its accent dot. Still never a large fill or default body text color — both new elements stay within the existing 24px-tall chrome-row footprint, so the 60/30/10 ratio at the whole-app level is unaffected.

## Language Switcher (DIST-01)

`LanguageSwitcher` — a compact, always-visible segmented pill with exactly two segments, "PT" and "EN". Not a cycling single-button toggle: showing both target languages at once (with the active one filled) is more discoverable for a bilingual community project than a single button whose current-vs-next state is implicit.

```
┌──────────┐
│ PT │ EN │   ← active segment (accent fill), inactive segment (muted text)
└──────────┘
```

- Container: `role="group"`, `aria-label={t("language.groupLabel", {ns:"common"})}`, inline-flex, min-height 24px (content-driven), padding 4px, border-radius 999 (pill), border 1px solid `var(--color-secondary)`, background transparent, gap 4px between segments.
- Segment (`<button>`): padding 4px 8px, border none, border-radius 999, Label typography (12px/600). Active: `background: var(--color-accent)`, `color: #ffffff`. Inactive: `background: transparent`, `color: var(--color-foreground)` at opacity 0.7 (hover: opacity 1, no background change — matches `SyncIndicator`'s existing muted-text hover discipline). `aria-pressed={isActive}`, `title`/`aria-label` = the full language name (`common.language.pt.full` / `.en.full`), visible text = the short code (`common.language.pt.short` / `.en.short`).
- Click: fires `i18n.changeLanguage(lng)` immediately (synchronous UI update via `react-i18next`'s re-render of every `useTranslation` consumer) AND `setLanguage(lng)` (persists to `app-store.ts`'s new `LANGUAGE_KEY`, fire-and-forget, no loading state needed for the persistence side — the visual language change is instant and does not wait on the write).
- **One accepted context-tradeoff (documented, not a bug):** the container's `var(--color-secondary)` border is reused verbatim from `HomeScreen.tsx`'s `ctaSecondaryStyle`, which reads clearly on the Home mount (transparent background against the dominant page background). In the in-project `Header` mount, the header's own background IS `var(--color-secondary)`, so this border is visually near-invisible there — accepted because the primary state signal is the active segment's accent fill, not the outer border; introducing a second, context-conditional border color for one small control was judged not worth the added component complexity for this phase's tiny UI surface.

**Mount points (both required, per `05-CONTEXT.md` — `Header` does not render on the Home view, so the switcher needs two homes to always be reachable):**

1. **In-project `Header`** (`src/shell/Header.tsx`) — rightmost, after `SyncIndicator`, inside the header's existing flex row (`gap: var(--spacing-md)` already applies, no new gap value needed).
2. **`HomeScreen` header** (`src/components/home/HomeScreen.tsx`) — rightmost of the existing right-aligned CTA group, after the "Novo projeto GSD" button, using that group's existing `gap: var(--spacing-sm)`.

Both mounts render the exact same `LanguageSwitcher` component with no props — active state is derived globally from `i18n.language`, so both instances (if somehow both were visible, which they never are since `Header` and `HomeScreen` are mutually exclusive per `view`) would always agree.

## Update Affordance (DIST-03)

`UpdateIndicator` — reuses `SyncIndicator`'s exact visual recipe (8px `statusDotVariants` dot + Label text + optional inline accent text-button, `gap: var(--spacing-sm)` flex row) rather than inventing a new "banner" pattern. This keeps the update notice visually family-consistent with the app's one existing "background health status" element and, per the mode instructions, non-intrusive by construction — it is a small chrome-row addition, never a modal, never a toast, never blocks the board or terminal.

**States:**

| State | Trigger | Visual |
|---|---|---|
| `checking` | App boot / periodic background re-check in flight | Renders nothing (`null`) |
| `up-to-date` | Check resolved, no newer version | Renders nothing (`null`) — silent by design, never announces "you're up to date" |
| `available` | Check resolved, newer version found | `accent` dot + `update.available.label` (title tooltip: `update.available.tooltip` with `{{version}}`) + inline accent text-button `update.available.action` |
| `downloading` | User clicked "Atualizar e reiniciar" | `accent` dot with `.status-dot--pulse` modifier + `update.downloading.label` interpolated with `{{percent}}`; the action button is removed (not disabled) for the duration |
| `error` | Download or install step failed | `warning` dot + `update.error.label` + inline accent text-button `update.error.action` ("Tentar novamente", re-attempts the same download) + trailing 16px `X` icon-button (`update.error.dismiss` a11y label) that hides the row until the next successful background check |

**Resolved discretion — one explicit click before restart, not a fully automatic download-and-relaunch:** `05-CONTEXT.md`'s `## Claude's Discretion` left "auto-baixar+relançar vs. banner 'atualizar agora'" open. This UI-SPEC resolves it as a single explicit user action ("Atualizar e reiniciar" triggers download, install, and relaunch together as one click, per `05-CONTEXT.md`'s "MVP pode baixar-e-instalar-e-relançar direto") — but that click must be user-initiated, never silent/automatic on check success. Rationale: this app's core value is keeping multiple live PTY terminal sessions running (Phase 2/4) — an unannounced automatic restart would kill every live `claude` session mid-conversation without warning, which is actively harmful for exactly this app's primary use case in a way it wouldn't be for a typical CRUD app. Requiring one click before the app touches any running session is the minimum safety bar, not extra friction.

**Mount points (both required, same reasoning as the language switcher):**

1. **In-project `Header`** — rightmost, after `LanguageSwitcher`.
2. **`HomeScreen` header** — rightmost, after `LanguageSwitcher`.

Both instances read from a single shared, module-level update-check state (not per-instance local state) so the indicator is consistent regardless of which view the user is on when a background check resolves — the check itself runs once at `AppShell` mount (per `05-CONTEXT.md`'s `check-update.ts`/`useEffect` design) regardless of `view`, since `AppShell`'s hooks run before its `view === "home"` early return.

## DIST-02 — No UI

Explicitly documented so the checker does not flag this requirement as missing a spec: **DIST-02 (packaged installer) has zero visual surface.** Its entire scope is `tauri.conf.json > bundle` config (icons already exist in `src-tauri/icons/`, only need referencing), per-target bundle sections (`nsis`/`linux`/`macOS`), and `.github/workflows/release.yml` CI. None of it renders in the app UI — the installer, SmartScreen warning (if any), and OS-native install dialogs are entirely outside this app's DOM/CSS control, same "system-rendered, no custom styling possible" treatment `04-UI-SPEC.md` already established for OS notifications.
