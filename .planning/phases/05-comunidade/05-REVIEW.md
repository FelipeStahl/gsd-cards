## Warnings

### WR-01: `getLanguage()` boot-restore chain has no `.catch` — an IPC/store-read failure produces an unhandled promise rejection instead of degrading like `checkForUpdate()` does

**Status:** Fixed (commit `3a6b4fb`) — `getLanguage()` boot-restore chain in `src/shell/AppShell.tsx` now `.catch(() => null)`s before `.then`, degrading to the same `navigator.language` fallback path as a missing saved value. Added a regression test (`AppShell.test.tsx`, "WR-01: getLanguage() rejeitado...") asserting a rejected `getLanguage()` produces zero unhandled rejections and still resolves the fallback language.

**File:** `src/shell/AppShell.tsx:41` (calls `src/persistence/app-store.ts:202-207`)
**Issue:** The phase's own stated design principle for boot-time plugin calls is "never throws — degrades to a safe default" (explicitly implemented for `checkForUpdate()`: `check().catch(() => null)` in `src/updates/check-update.ts:30`). `getLanguage()` does not follow the same discipline: it enum-validates a *successfully returned* value (defends against T-05-01, a tampered/corrupted string), but it never wraps the `appStore.get()` call itself in a try/catch or `.catch()`. In `AppShell.tsx`'s boot effect:
```ts
void getLanguage().then((saved) => { ... });
```
there is no `.catch()` on this chain. If `appStore.get()` rejects — e.g. the underlying `tauri-plugin-store` IPC call fails, the store file is locked, or the app-data directory is unreadable — the rejection is unhandled. In a webview this typically only logs a console warning rather than crashing the render tree, but it means the `navigator.language` fallback (the intended safety net for "no usable saved language") never runs in this failure mode, and the behavior is inconsistent with the sibling `checkForUpdate()` effect three lines below it in the same component, which explicitly cannot suffer this class of failure.
**Fix:**
```ts
// src/shell/AppShell.tsx
void getLanguage()
  .catch(() => null)
  .then((saved) => {
    if (cancelled) return;
    if (saved) {
      if (saved !== i18n.language) void i18n.changeLanguage(saved);
      return;
    }
    if (navigator.language.toLowerCase().startsWith("en")) {
      void i18n.changeLanguage("en");
    }
  });
```
(Equivalently, `getLanguage()` itself could swallow read errors and resolve `null`, matching `getRecents()`'s `?? []` degrade-to-empty convention — but note `getRecents()` in `HomeScreen.tsx:69` has this same pre-existing gap and is out of this phase's diff, so fixing only `getLanguage()`/the new boot effect is the minimal in-scope change.)

### IN-01: `dtolnay/rust-toolchain@stable` sets both macOS targets on every macOS matrix leg, though each leg only builds one

**Status:** Fixed (commit `388c3d1`) — added a `target` field to each matrix `include` entry (per-leg target, empty string for Linux/Windows) and changed `targets: ${{ matrix.platform == 'macos-latest' && '...' || '' }}` to `targets: ${{ matrix.target }}`, so each macOS leg installs only the Rust target it actually builds.

**File:** `.github/workflows/release.yml:48-51`
**Issue:** `targets: ${{ matrix.platform == 'macos-latest' && 'aarch64-apple-darwin,x86_64-apple-darwin' || '' }}` installs both Rust targets on *both* `macos-latest` matrix legs, even though one leg builds `--target aarch64-apple-darwin` and the other `--target x86_64-apple-darwin` (line 17-19). Not a correctness bug (the unused target is simply installed and never invoked) and performance is explicitly out of scope for this review, but it's a one-line simplification that removes redundant toolchain setup work per CI run.
**Fix:** Scope the target list per-leg via a matrix field instead of a platform-wide conditional, e.g. add `target: 'aarch64-apple-darwin'` / `target: 'x86_64-apple-darwin'` to each macOS `include` entry and reference `matrix.target` in the `targets:` input (falling back to `''` for the other platforms).

### IN-02: `LanguageSwitcher`'s `active` fallback and `getLanguage()`'s enum guard duplicate the same `SUPPORTED_LANGUAGES.includes(...)` check with slightly different casts

**Status:** Fixed (commit `3536093`) — added `export function isSupportedLanguage(value: string): value is SupportedLanguage` to `src/persistence/app-store.ts`; both `getLanguage()` (same file) and `LanguageSwitcher.tsx`'s `active` derivation now call it directly, removing the duplicated `(SUPPORTED_LANGUAGES as readonly string[]).includes(...)` + `as SupportedLanguage` cast pattern. Behavior unchanged; test module mocks (`LanguageSwitcher.test.tsx`, `AppShell.test.tsx`, `HomeScreen.test.tsx`) updated to export the new guard.

**File:** `src/shell/LanguageSwitcher.tsx:59-63`, `src/persistence/app-store.ts:204-206`
**Issue:** Both sites independently re-implement "is this string a member of the closed `pt-BR | en` enum" via `(SUPPORTED_LANGUAGES as readonly string[]).includes(x)` followed by an `as SupportedLanguage` cast. This is intentional defense-in-depth (one guards untrusted persisted data, the other guards a rare out-of-enum `i18n.language` value during external-detector transitions) and is not a bug, but a shared `isSupportedLanguage(x: string): x is SupportedLanguage` type-guard in `app-store.ts` (already exporting `SUPPORTED_LANGUAGES`/`SupportedLanguage`) would remove the duplicated cast pattern and let both call sites use `if (isSupportedLanguage(x))` without a manual `as` assertion.
**Fix:**
```ts
// src/persistence/app-store.ts — additive export
export function isSupportedLanguage(value: string): value is SupportedLanguage {
  return (SUPPORTED_LANGUAGES as readonly string[]).includes(value);
}
```
Then both `getLanguage()` and `LanguageSwitcher`'s `active` derivation can call `isSupportedLanguage(...)` directly instead of repeating the cast.
